# Отчёт учредителям ООО «ОМЕГА» (клиника «Форма»)

Сборка ежемесячного отчёта учредителям: **один файл ввода → HTML-отчёт + Excel-расшифровка**.

Раньше отчёт собирался из трёх разных файлов бухгалтерии (БАНК, ВЫРУЧКА, РАСХОДЫ)
с ручным расчётным блоком внутри. Теперь:

* данные вводятся в **один файл** из шести листов (`templates/Ввод-данных-<Месяц>-<Год>.xlsx`);
* все расчёты — в коде, а не в ячейках: методику нельзя случайно сломать протяжкой формулы;
* Excel на выходе — **расшифровка**: на каждую цифру отчёта есть формула и ссылка на источник;
* контрольные сверки считаются автоматически и печатаются при сборке.

## Как собрать отчёт за месяц

```bash
# 1. создать пустой файл ввода на нужный месяц
python3 -c "import sys; sys.path.insert(0,'tools'); import input_xlsx; \
  input_xlsx.make_template('templates/Ввод-данных-Август-2026.xlsx', 2026, 8)"

# 2. заполнить его данными (см. DATA_REQUEST.md — что и откуда выгружать)

# 3. собрать отчёт и расшифровку
python3 tools/build.py --input "templates/Ввод-данных-Август-2026.xlsx" --year 2026 --month 8
```

На выходе в `out/`:

| Файл | Что это |
|---|---|
| `otchet-<год>-<месяц>.html` | отчёт учредителям: один самодостаточный файл, открывается с телефона |
| `Расшифровка-отчёта-<Месяц>-<Год>.xlsx` | приложение: откуда взялась каждая цифра |

Сборка печатает контрольные сверки. Если хоть одна помечена `РАСХОЖДЕНИЕ` —
отчёт публиковать нельзя, сначала разбираемся с расхождением.

## Тексты в отчёте

Резюме месяца и блок «фокус на следующий месяц» генерируются из цифр.
Чтобы задать свои формулировки — передать JSON:

```bash
python3 tools/build.py --input ... --narrative narrative-2026-08.json
```

```json
{
  "summary": [{"h": "Заголовок тезиса", "p": "Текст с <b>выделением</b>."}],
  "focus":   [{"h": "Заголовок", "p": "Текст"}]
}
```

## Проверка на эталоне

Июнь 2026 — уже сверенный бухгалтерией месяц, он лежит в репозитории как эталон.

```bash
python3 tools/june_source.py     # три старых файла -> канонические данные
python3 tools/build.py --canon data/canonical/2026-06.json
python3 tools/roundtrip_test.py  # старый формат -> новый формат -> те же цифры
```

`roundtrip_test.py` проверяет, что новый формат ввода воспроизводит июньский
отчёт до рубля: выручка, расходы, доход и «к выплате» по каждому учредителю,
итог водопада, остаток на счёте, рост с начала года.


## Обмен УМЦ → 1С:Бухгалтерия

Отдельный блок: довести файл обмена до загрузки и сверить кассу с ОФД.

**Приложение** — один файл, открывается двойным щелчком, работает без интернета,
ничего никуда не отправляет:

```bash
npm install xlsx@0.18.5 --no-save
python3 tools/obmen_app/build.py     # -> out/obmen.html
```

Кладёте в него до четырёх файлов — выгрузку XML (обязательно), отчёт
«Такском-Касса», реестр услуг и реестр оплат. Что в какую ячейку положить,
неважно: таблицы распознаются по содержимому.

Что показывает:

1. **Итог** — можно грузить или сначала чинить УМЦ, и почему именно.
2. **Состав выгрузки** с проводками по каждому виду документа.
3. **Доводка** — что подставлено молча, что вынесено на ваши глаза.
4. **Сверка с ОФД** день в день: наличные, карты, зачёт аванса; отдельно
   эквайринг по терминалам — так ловится оплата, заведённая не на тот терминал.
   Строку оплаты без эквайрингового терминала приложение **разбирает само**:
   возврат зачтённого аванса (денег не двигалось, терминала у него нет и быть
   не может) убирается из «Возврата оплаты» с уменьшением зачёта на ту же сумму,
   а обычной оплате терминал проставляется, если в этот день ровно одному
   терминалу не хватает ровно этой суммы. Такая строка иначе не даёт документу
   провестись.
   Возврат, который касса пробила, а в программе не оформили, приложение
   **проводит само**: доказательство — чек возврата в ОФД ровно на эту сумму
   в тот же день, номенклатура берётся та, которой пользуются возвраты в самом
   файле. Выручка и эквайринг уменьшаются, наличные не двигаются.
   Кассу, которая в выгрузку не попадает вовсе, приложение умеет **дописать
   из фискальных данных** — но только если по ней все чеки авансовые: аванс не
   требует номенклатуры, которой в ОФД нет. В отчёт о розничных продажах
   добавляются предоплата и оплата на одну сумму, наличные при этом не двигаются,
   потому что считаются остатком. Проводка Дт 57.03 Кт 62.Р. Правка добавляет
   в файл деньги, поэтому по умолчанию выключена.
   Оплату, заведённую не на тот терминал, приложение **переставляет само**: если за день у одного терминала
   ровно столько же лишних денег, сколько у другого не хватает, основание железное —
   фискальный накопитель. Сумма документа не меняется, меняется только аналитика
   на счёте 57.03. В самой УМЦ ошибка при этом остаётся, о чём приложение и говорит.
5. **Три источника об одних деньгах** — УМЦ против ОФД против выгрузки, по дням
   и терминалам. Разрыв УМЦ↔ОФД лечится в программе, разрыв ОФД↔выгрузка —
   настройкой обмена, и без такой разбивки эти две болезни сливаются в одну цифру.
   Терминал берётся из реестра оплат: его надо добавить в отчёт полем
   «Эквайринговый терминал», тогда он приклеивается к названию документа
   после запятой. Терминалы, у которых в реестре видна лишь часть денег
   (оплата заведена прямо в оказании услуг), в таблицу не берутся.
6. **Платежи, заведённые вручную** — у них время 00:00:00 и нет привязки к чеку,
   поэтому фильтр фискализации выкидывает их из выгрузки, хотя деньги настоящие
   и чек в ОФД есть. Это и даёт систематический недобор по терминалу: за август
   61 такой платёж на 522 000 ₽ при недоборе облачной кассы 513 500 ₽, а 16 и
   17 августа сходится до рубля.
7. **Чеки** — услуги без пробитого чека и сравнение реестра с выгрузкой по дням.
8. **Задвоение** — считается по деньгам, а не по количеству документов: если
   администратор перевесил оплату на правильный документ, а лишний пометил на
   удаление, в реестре услуг обе половинки стоят плюсом, а в реестре оплат у
   близнеца минус. Погашенные пары отделены от настоящих.
9. **Памятка** по загрузке в бухгалтерию, по шагам.

Кнопка отдаёт исправленный файл.

**То же самое из командной строки:**

```bash
python3 tools/xml_fix.py выгрузка.xml                       # доводка
python3 tools/xml_exchange.py выгрузка-исправленный.xml \
        --taksk Такском.xlsx                                # сверка с ОФД
```

Настройки подстановки (склад, статьи ДДС, розничный покупатель) —
`tools/obmen-nastroyki.json`; в приложении те же поля лежат под «Настройки
подстановки» и хранятся в браузере.

**Кассы.** В файле обмена поля «Касса» нет, а среди 48 правил конвертации нет
правила для справочника «Кассы» — обработчик жёстко ставит `СчетКасса =
КассаОрганизации`. Значит обе кассы клиники в бухгалтерии сливаются в одну, и
передать разделение через этот обмен нечем. Приложение определяет кассу по
префиксу в номере документа (`ПКО №К1000000013`) и использует это, чтобы найти
перемещения между кассами. Дальше на выбор: оформить пару через 57.01 — у
приходного ордера вид операции меняется на «Прочий приход», и обработчик правила
подставляет ему счёт из настройки УМЦ `битСчетУчетаПрочегоПриходаПКО`, так что
поставьте там 57.01 и пара закроется в ноль, — выбросить из файла или оставить
как есть. По умолчанию первое: оба документа остаются в кассовой книге, а фантома
на 57.01 и на расчётном счёте не появляется.

**По одному дню.** Обработка в УМЦ умеет отдавать день за днём — приложение
это понимает: фискальные данные обрезаются по периоду файла обмена, поэтому
месячный отчёт ОФД можно не перевыгружать. Несколько дневных файлов кладутся
в ячейку обмена разом и склеиваются в один, с пересчётом внутренней нумерации
`Нпп` (иначе ссылки одного файла попадут на объекты другого). Пропущенные дни
внутри периода называются отдельно.

**Проверка на эталоне.** 01–14.09.2026 лежит в `data/source/2026-09`:
наличная выручка сходится с ОФД все четырнадцать дней до рубля (22 221 300 ₽),
каждый терминал сходится со своей кассой (Корпус 1 — 20 512 380 ₽ в ноль).

```bash
npm install xlsx@0.18.5 playwright@1.49.1 --no-save
node tools/obmen_app/test.mjs
```

Разбор периода можно посмотреть текстом, не открывая браузер, — так его удобно
грепать. Файлы скрипт выбирает из `data/source/<период>` сам, по именам:

```bash
node tools/obmen_app/show.mjs 2026-08
node tools/obmen_app/show.mjs 2026-09 | sed -n '/§ 3/,/§ 4/p'
```

## Структура

```
tools/june_source.py     разбор трёх старых файлов бухгалтерии -> канонические данные
tools/input_xlsx.py      единый файл ввода: генерация шаблона и чтение (+ дедупликация)
tools/model.py           расчётная модель: KPI, водопад, методика учредителей, сверки
tools/workbook.py        Excel-расшифровка (10 листов)
tools/report_html.py     HTML-отчёт (11 разделов, mobile-first)
tools/build.py           CLI сборки
tools/xml_exchange.py    разбор файла обмена с БП и сверка кассы с ОФД
tools/xml_fix.py         доводка файла обмена до загрузки в бухгалтерию
tools/obmen_app/         приложение «Обмен УМЦ → Бухгалтерия» (сборка, тест, разбор периода)
tools/roundtrip_test.py  проверка нового формата на эталоне июня
data/source/             исходные файлы за июнь 2026 (эталон)
data/canonical/          канонические данные по месяцам (JSON)
templates/               пустые файлы ввода
docs/                    пример готового отчёта за июнь
out/                     результаты сборки
```

Документы: [DATA_REQUEST.md](DATA_REQUEST.md) — что выгружать,
[METHODOLOGY.md](METHODOLOGY.md) — как считается доход учредителей и что важно знать о цифрах.
